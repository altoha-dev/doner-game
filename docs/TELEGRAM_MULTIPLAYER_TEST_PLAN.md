Пакетный input protocol 6.1.6 требует согласованного обновления API/frontend и reload открытых клиентов. Все четыре персонажа, включая Ayazhan (`ayazhan`), бесплатны в комнате.

## Безопасный порядок публикации

1. Просмотреть изменения и [отчёт](STAGE_6_1_REPORT.md), сохранить актуальный backup существующей PostgreSQL. Новая migration только добавляет таблицы; `migrate reset`/`db push` не нужны.
2. Когда будет принято решение публиковать, сделать commit/push самостоятельно. Если frontend автоматически публикуется по push, отложить его релиз до готовности backend/schema. Не выпускать новый frontend первым.
3. В существующем Railway API оставить DATABASE_URL, BOT_TOKEN, JWT_SECRET, CORS_ORIGINS и domain. Для invite links добавить **BOT_USERNAME** — публичное имя того же бота из существующей bot configuration, без `@`. Новых секретов и frontend variables нет. Без BOT_USERNAME остаётся рабочим вход по коду.
4. Один активный API instance. При обновлениях версии, уже обслуживающей rooms, сначала остановить старый instance: в этой реализации нет lease для одновременной работы двух RoomManager. Допустить короткое окно обслуживания. Настройка overlap=0 сама по себе не гарантирует отсутствие одновременного startup старого и нового процесса. Railway позволяет настраивать overlap/draining; порядок нужно согласовать с этим ограничением. [Deployment teardown](https://docs.railway.com/deployments/deployment-teardown).
5. Собрать API прежней командой `pnpm install --frozen-lockfile --prod=false && pnpm build:api`. Node 24, pnpm 10.34.6. Сохранить доступность Prisma CLI в образе для migration hook (существующая настройка prune dependencies).
6. **До старта нового API** выполнить существующий pre-deploy hook `pnpm db:deploy` в Railway environment. Ожидается применение `20261020000000_party_rooms` после двух прежних migrations. Не создавать вторую migration на те же поля. Если hook завершился ошибкой, не запускать новую версию и не продолжать frontend rollout. Railway pre-deploy запускается после build и до serving, с environment/private network. [Pre-deploy commands](https://docs.railway.com/deployments/pre-deploy-command).
7. Запустить `pnpm start:api` на прежнем Railway PORT/domain; `/health` должен вернуть `{"status":"ok"}`. Сервер слушает `0.0.0.0`. REST и Socket.IO используют тот же HTTP server. Новый сервис/порт для realtime не требуется.
8. Проверить `/auth/telegram` и `/me` через настоящий Mini App: имя, selected character, Doner/Golden Doner прежние. `/health` сам по себе не подтверждает работу sockets.
9. Собрать и опубликовать frontend в существующем Vercel project: install `pnpm install --frozen-lockfile`, build `pnpm build:web`, output `apps/web/dist`. **Сохранить production VITE_API_URL**, не копировать `http://127.0.0.1:3014` из QA. В репозитории QA URL не записан в `.env`.
10. Открыть Mini App из существующего бота. В диагностике соединений проверить `/socket.io/` на прежнем API domain: WebSocket connection или работающий polling fallback. JWT находится в handshake auth payload, не query string. Не публиковать HAR/frames с credentials.
11. При CORS ошибке сверить точный frontend origin с CORS_ORIGINS. Не добавлять `*`. При отсутствии связи проверить доступность `/socket.io/` через proxy. REST и socket CORS настроены одинаково; корректный `/health` не исключает proxy/auth ошибку sockets.
12. Выполнить сценарий двух телефонов ниже. BotFather Main Mini App URL должен оставаться действующим HTTPS frontend. Формат Main Mini App invite подтверждён [документацией Telegram](https://core.telegram.org/bots/webapps#launching-the-main-mini-app).

Для последующих restart действует документированное поведение: активный RACE прерывается, unfinished → ABORTED, уже принятые финиши/blocks сохраняются. При rollback приложения additive таблицы можно оставить; не удалять пользовательские данные или миграции ради отката.

## Два реальных телефона / два аккаунта

Подготовить телефон A и телефон B с **разными Telegram accounts**. Желательно проверить iOS + Android и разные сети. До начала записать оба Doner/Golden Doner, выбранных/открытых героев. Не использовать два окна одного аккаунта: второе намеренно отключает первое.

## Потеря сети и refresh

1. Создать новый матч, поставить два блока, начать RACE. Запомнить code, число игроков и блоков.
2. На B отключить Wi-Fi и мобильную сеть на 10–20 секунд. A продолжает движение; по heartbeat появляется отсутствие связи B. На B управление блокируется, после обнаружения socket loss — reconnect banner.
3. Включить сеть до deadline. B возвращается в **ту же** комнату/seat: 2 участника, те же blocks/round, принятая сервером позиция. Второго B нет. Возможна коррекция после задержки; матч не начинается заново.
4. Обновить Mini App на B. Повторная авторизация и полный snapshot возвращают в текущую фазу. Если гонка уже завершилась, отображаются RESULTS, а не старый RACE.
5. В новом lobby отключить A более чем на 30 секунд после обнаруженного disconnect; B становится host. Вернувшийся A не отбирает host обратно.
6. В отдельном раунде оставить B без сети до истечения 90s: у A RESULTS с DNF B; вернувшийся B получает те же результаты.
7. Открыть второй экземпляр Mini App тем же аккаунтом: старый получает сообщение о подключении в другом окне, в комнате остаётся один участник этого аккаунта.

## Дополнительные приёмочные проверки

- Создать комнату capacity 4, пригласить ещё двух разных пользователей: отдельные seats, имена/READY/по блоку, максимум четыре. Автоматический основной browser scenario проверяет двух; четыре физических устройства ещё не проверялись.
- Неверный/закрытый code показывает понятную ошибку. Заполненная комната не принимает нового участника; после старта новые JOIN отклоняются.
- Проверить крупный/длинный кириллический first_name и avatar, 320/375/390/430/500px, landscape/малую высоту, safe areas Telegram.
- При недоступном Clipboard API текст для копирования доступен в поле; сообщение не обещает успешное копирование.
- На отдельном staging/local окружении перезапустить API во время RACE: общие RESULTS, unfinished ABORTED, blocks остаются, host может NEXT. Не перезапускать production для этого без согласованного окна.
- Пройти пять раундов: завершение матча, затем новая комната с пустой картой.

Зафиксировать device/OS/Telegram version/network, room code, шаг и результат. Не прикладывать initData/JWT/secrets. До выполнения этого сценария ручная Telegram приёмка остаётся **не выполнена**.
